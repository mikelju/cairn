# Deferred security findings

| ID | Severity | Where | What happens | Status | Origin |
| --- | --- | --- | --- | --- | --- |
| SEC-001 | Medium | `POST /jobs`, `/api/tools/{name}` (all registry tools since phase 02a) and `POST /step/2/run` (replays the full loop with DuckDB and a study validation per request, phase 02b) | Public unauthenticated endpoints with unbounded in-memory job dicts, and study tools that each open DuckDB and run several queries per request, can be abused for memory and CPU on the public demo. | Accepted demo risk (phase 06, O1 A): the access code gates only the live Explore route, which is the one path that spends Bedrock money; these other endpoints run no model, so they cost CPU and memory, not Bedrock. Per-user identity and rate limits are SIMULATED and named in "In production". | Phase 01, widened in phase 02a and 02b, and in phase 03 (`search_guidance`, `/step/3`, `/explore/run`, `/highlight/{id}`, `/highlights/{name}`), and in phase 04 (`GET /step/4` and `POST /api/threads` create a thread, run gather and keep it in an unbounded SQLite checkpointer, `:memory:` by default), and in phase 05 (`GET /step/6` and `GET /api/threads/{id}/audit/verify` read the chain per request; the `audit` table is unbounded and unauthenticated refusals add entries to it; the per-thread lock map grows with every thread) |
| SEC-002 | Low | `src/cairn/observation.py` `snapshot_sha256` | The snapshot hash comes from the manifest, not from the DuckDB file queried; a stale or altered `data/build/cairn.duckdb` yields Observations that claim the pinned snapshot. | Fixed in phase 05: the build records its snapshot in a `build` table; the app refuses to start (`StaleBuild`) and `gather_state` fails if it differs from the manifest, so the tools, step 2, Explore and MCP never run on a stale build. Regressions: `tests/test_audit.py::test_snapshot_*`. | Phase 02a |
| SEC-003 | Low | `src/cairn/retrieval.py` lazy reranker load and `src/cairn/tools.py` `_live_index` (record and live modes) | Concurrent first requests in live mode each build the index and load the 0.57 GB reranker without a lock, and the query has no length limit; peak memory can take the container down. The deployed container runs replay, so this is not reachable today. | Fixed in phase 06: a lock around the lazy index build (`tools._live_index`) and around the lazy reranker load (`Index.rerank`), and a 500-character limit on the live question checked before any model or retrieval call. Regressions: `tests/test_explore_live.py::test_live_index_*`, `test_explore_live_refuses_*`. | Phase 03 (R101) |
| SEC-004 | Low | `Makefile` `deploy` with `SKIP_BUILD=1` and `.github/workflows/image.yml` | The deploy pushes whatever local image is tagged `cairn`; nothing ties it to the workflow artifact by digest, so an older or local build can be deployed by mistake (the footer commit shows it, but nothing blocks it). | Open; operator check of the footer commit after each deploy. | Phase 03 (R101) |
| SEC-005 | Low | `.github/workflows/*.yml` actions and `Dockerfile` base images | Actions and base images are pinned by mutable tag, not by SHA or digest; a rewritten upstream tag would run foreign code with `contents: read` and could alter the image artifact. | Open; supply-chain hardening, same pattern as before phase 03. | Phase 03 (R101) |
